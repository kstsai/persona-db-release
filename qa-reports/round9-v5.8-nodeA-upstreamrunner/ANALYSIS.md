### 4.6 其他觀察

**(1) `status='ok'` 但回傳 0 筆 —— 兩次探針都出現**【證據】

| 請求 | `status` | `total_matched` | `returned` | `pool_exhausted` | `stop_reason` |
|:--|:--|--:|--:|:--|:--|
| `t1`（窄查詢, top_k=10） | **`'ok'`** | **0** | **0** | `True` | `no_op_limit` |
| `t2`（窄查詢, top_k=100） | **`'ok'`** | **0** | **0** | `True` | `no_op_limit` |

部署碼（`server.py` L522）為：
`status = "ok" if len(matched) >= TARGET_MIN else "too_strict" if loop >= max_loops and len(matched) == 0 else "ok"`
→ `'too_strict'` 需要**跑滿 3 輪**且 matched=0；這兩次在 loop=2 就因 `no_op_limit` 停住，
於是**回傳 0 筆卻報 `status='ok'`**。只讀 `status` 的消費端會把「查無資料」當成成功。
（緩解：`returned=0` 與 `pool_exhausted=True` 都在回應裡，資訊沒有消失，但 `status` 具有誤導性。）

**(2) 503 錯誤是契約合規的，但 `details` 的指引可能誤導維運**【證據】（回應 + 伺服器端 log 兩側都有）

- 探針 `t3`（`questions=目標客戶`）→ `503`，body 為宣告的 `ErrorResponse` 形狀：
  `{"status":"error","error":{"code":"FILTER_FAILED","message":"無法從問題中解析出篩選條件（LLM 分析失敗且關鍵字解析無結果）","details":"請確認 LLM API key / model 設定，或換一種問法","retryable":true}}`
- **伺服器端 log**：`LLM returned no filters, falling back to keyword parsing` → **LLM 呼叫本身成功**（沒有失敗、沒有逾時、沒有截斷）。
- 也就是說：`message` 寫「LLM 分析失敗」、`details` 建議「檢查 API key / model 設定」，
  但真因是「**LLM 正常回應，但對這個問題產生不出任何篩選條件**」。維運照著 `details` 去查金鑰與模型會查錯方向。
- 正面：系統**寧可回 503 也不編造**名單；且錯誤走統一的 `ErrorResponse` 形狀（把 `#47` 的涵蓋從 400 延伸到 503）。

**(3) 契約宣告了兩個不可達的停止原因**【源碼層證據，非回應可觀測】

`broadening_stop_reason` 宣告 9 個值（含空字串）。依部署碼（sha 已驗）：

| 值 | 可達性 | 依據 |
|:--|:--|:--|
| `""`（空字串＝未進入迴圈） | **不可達** | 候選查詢函式只有兩個 `CandidatesResponse` 回傳點（L525、L604），**兩者都帶入 `stop_reason`**；且迴圈後有 `if not stop_reason:` 補值（覆蓋 4 種情況）⇒ 不可能留空 |
| `budget_limit` | **不可達** | `tokens_spent` 初值 12000、`TOKEN_BUDGET=40000`、`broaden_max_tokens=8000`、`max_loops=3` ⇒ 預算只可能在**跑滿 3 輪後**才擋住下一輪，而分類順序 `target_reached → loop_limit → no_filters → budget_limit` 會先命中 `loop_limit` |
| 其餘 6 值 | 未在本輪觀測到 | 見 §5 |

消費端若 `switch` 這個欄位，這兩支分支實務上永遠不會被走到。無害，但屬「宣告與行為的落差」。
**再次強調：這是讀部署碼的推論，不是回應觀測到的現象，也無法用回應否證。**

## 6. 結論

### 6.1 這版好在哪（正面）

1. **核心語意護欄是有效的**：業主語意必套 `employment_status`（4/4 可重現）、
   藥妝零售不誤套醫美維度、小吃攤顧客語意不誤套就業狀態 —— 而且模型的 `reasoning`
   會自己講出判準（「問題主體是顧客，不是業者本人」），可審計。**【證據】**
2. **契約完整、錯誤處理合規**：`#47`（400 統一形狀）、`#48`（可觀測性欄位入 OpenAPI）、
   `#49`（`opMode` 預設合法）、`#44`（`scoring_basis` 三欄齊備）全 ✅；
   本輪額外觸發 503，**錯誤也走同一套 `ErrorResponse` 形狀**。
3. **可觀測性缺口為零**：`summary` 曝露 24 欄，`applied_filters`／`dims_counted`
   的維度**全部**可在回應內自我驗證（15/15 項通過）。這是本輪最乾淨的一項。
4. **計分宣告誠實**：9 個具檢定效力的配對中，**(b) 同向量不同分 = 0**，
   沒有發現「有未列出的維度在偷偷影響分數」。`score_scale` 也誠實宣告為 response 內相對分。
5. **`#56` 的新欄位與新上限是有效的**：10 輪放寬中 `no_op` 只有 1 輪（10%），
   連續空轉上限（≤2）成立，且**旗標與數字 10/10 一致**；停止原因讓「為何沒達到目標」變成可判讀。
6. **資料不足時不編造**：`matched=0` 時回 `returned=0`（不硬湊）、
   語意無法解析時回 503 而不是給一份隨機名單。`overshoot` 旗標也正確標出 7.25× 的失控放寬。

### 6.3 建議

1. **把「核心維度不可被放寬」變成機制，而不只是告警**：`#42` 已能偵測，但目前只印 ⚠️。
   建議在放寬步驟傳入 `reinforced_dims`（分析步驟宣告的必要維度）並**硬性禁止移除**，
   或在移除核心維度時**不要**把它從 `applied_filters` 拿掉（改為標記 `relaxed_core_dims`）。案例 07 的 8→58 是直接證據。
2. **讓 `status` 反映實情**：`matched == 0` 時不該是 `'ok'`（例如 `'empty'`／`'too_strict'` 不受 `loop>=max_loops` 限制）。
3. **區分兩種 `no_op`**（嘗試失敗 vs 刻意拒絕），或改用不同的停止原因值。
4. **修正 503 的指引文字**：`details` 應區分「LLM 呼叫失敗」與「LLM 回應但無 filter」（前者才查金鑰）；
   `retryable` 對後者是否為 `true` 值得再想（同一個泛問題重試大概還是失敗，雖然 LLM 有隨機性）。
5. **清掉不可達的列舉值**（`""`、`budget_limit`），或調整分類順序讓它們真的可達。
6. **對「單次執行」的品管流程加註**：任何以單次 sweep 為依據的品質結論都應附取樣分布
   （本輪案例 06 的四次結果差異足以推翻單次判讀）。
