## 缺陷 1：我第一次啟動時，runner 寫進了**上一輪的目錄**（第九輪）

| | 內容 |
|:--|:--|
| 症狀 | 第一次啟動後 `~/qa-round10/` 一直是空的（`run.log` 不存在、沒有 `meta/*.meta`） |
| 成因 | 我複製第九輪的工具來開第十輪，**忘了改 runner 裡寫死的 `OUT="$HOME/qa-round9"`**。所以 v5.10 的執行把證據寫進了**第九輪在節點上的工作副本**。 |
| **影響範圍** | **僅限節點上的 `~/qa-round9/` 那一份工作副本**（可拋棄）。以下全部不受影響（已逐項驗證）：<br>• 本機 master：`raw/00_status.body` 仍是 **v5.8**、`run.log` sha256 `2fe52c27ebefe32a`、571 行（= 原本的值）<br>• 已發布的 repo 版本：`raw/00_status.body` 仍是 v5.8、`run.log` 571 行、`git show HEAD:` 內容一致<br>• 本輪（第十輪）的證據：第一次啟動**沒有產生任何可用結果**（7 個檔被寫進舊目錄後即中止，且沒有任何案例走完） |
| 具體污染 | 節點 `~/qa-round9/` 有 **7 個檔**被覆寫：`raw/00_status.body`（變成 v5.10）、`raw/01_kangshimei.body`、`headers/00_status.headers`、`headers/01_kangshimei.headers`、`meta/00_status.meta`、`meta/00_status.w`、`meta/01_kangshimei.w`；`run.log` 因 `tee -a`（append）被**追加**了 v5.10 的輸出。其餘 8 個案例的證據與 `probe/` 仍是 9/14 的原檔。 |
| 處置 | ① 節點上該目錄**更名為 `~/qa-round9-POLLUTED-by-round10-attempt/`**（讓它不可能被誤認為乾淨的第九輪證據）<br>② `meta/aborted-attempt-runner-efa7f666.sh` 保留那次實際執行的 runner（可複驗它寫死 `qa-round9`）<br>③ **修法（結構性）**：`make-runner.py` 改為**由本目錄名推導** `OUT` 預設值（`round10-*` → `$HOME/qa-round10`），並加三道產生後檢查：必須含推導值、**不得**再出現 `qa-round9` |
| 教訓 | 這正是 skill Pitfalls 那條「**工具檔有寫死的目錄預設值時，新增目錄後沒同步**」的實例 —— 只是後果比「靜默少算幾筆」更嚴重：**會就地覆寫已發布的證據**。跨輪複製工具時，必須逐一檢查所有寫死的路徑預設值。 |

## 缺陷 3：診斷期間曾同時有兩個 runner 實例

| | 內容 |
|:--|:--|
| 症狀 | 我第一次啟動的實例「看起來沒動」（其實是寫到舊目錄），於是又跑了一次前景診斷 → **同時有兩個實例** |
| 影響 | 兩個實例都寫進 `~/qa-round9/`（同一組檔名），互相覆寫。因為**兩者都沒有走完任何一個完整案例**（診斷那次被 30 秒 timeout 砍掉，第一次啟動在案例 01 途中被 `pkill`），所以**沒有產出任何被誤用的證據**。 |
| 確認 | 兩個實例都已終止；本輪的證據是在**乾淨重建**的 `~/qa-round10/` 上、**單一實例**跑出來的 |
| 教訓 | 啟動後若看不到預期輸出，**先確認證據落點與程序狀態，不要直接再跑一次** |
