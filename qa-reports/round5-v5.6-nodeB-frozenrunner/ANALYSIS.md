## 2. 本版契約變更（Step 6）—— 第四種契約，且**直接回應本系列先前發現**

`raw/openapi.json`：10131 B → **12332 B**（+2201），sha256 `aafe647f46ee8abe`。endpoint 與 persona 維度（25）**均未變**。

### 2.1 新增兩個**型別化** schema（本輪最重要的變更）

| 新 schema | 描述原文 | 對應 issue |
|:---|:---|:---|
| `BroadeningAttempt` | 「broadening loop 的一次嘗試（**#48：型別化，讓 OpenAPI 產生 properties 而非 additionalProperties —— codegen/驗證工具才看得到這些欄位**）」 | **#48** |
| `ScoringBasis` | 「scoring 演算法說明（**#48：型別化**）。`score_scale` 明示 score 僅供版本內相對排序。」 | #48 / #44 |

**這正是我在 v5.4 報告 §2.3 提出的問題**：

> 「新欄位只有文字描述、無機器可讀 schema —— codegen / schema 驗證工具不會產生 `pool_exhausted`、`score_scale` 等欄位；consumer 必須靠讀描述或實際回應才能發現。**建議改為顯式 `properties`。**」

v5.4 時 `broadening_attempts` items 與 `scoring_basis` 都是 `{"additionalProperties": true, "type": "object"}`；**v5.6 已改為 `$ref` 指向型別化 schema** ⇒ codegen 現在看得到全部欄位。**✅ 已修正。**

### 2.2 欄位語意補強

| 欄位 | v5.4 | **v5.6** |
|:---|:---|:---|
| `overshoot` | 「放寬後**過頭**」（未量化） | **「放寬後樣本數 > 2×TARGET_MIN」** ← 首次給出可判定的定義 |
| `score_scale` | 「分數尺度語意」 | **「分數尺度語意；不可跨版本比較」** ← 我 v5.3.1 §5.9 的建議已寫入契約 |
| `relaxed_dims_scored_at` | 「被放寬維度的計分處理方式」 | 加註 **「Q3-A': 不計分 → null」**（決策 ID 可追溯） |
| `weight_version` | 「權重表版本」 | 加註 **「換版代表分數尺度改變」** |

### 2.3 ⚠️ 行為變更：`opMode` 預設值改了

```
v5.4: opMode default = "兩者皆可"
v5.6: opMode default = "僅篩選"     ← 變更
```

**影響範圍**：只有**未明確傳 `opMode`** 的呼叫者。本測試 runner 一律明傳 `opMode=僅篩選`，**故本輪結果不受影響、且與前四輪仍可比**。
**但對其他 consumer 是 breaking change** —— 未傳 `opMode` 者行為會從「兩者皆可」變成「僅篩選」。

### 2.4 新增 `BroadeningAttempt` 帶來的可驗證性

因為現在有明確的 `overshoot` 定義（> 2×TARGET_MIN），未來可**獨立驗證**該旗標是否算對 —— v5.4 時不可能（描述未量化）。

## 7. 結論

### v5.6 的實質改善 ✅
1. **契約型別化**（`BroadeningAttempt` #48、`ScoringBasis` #48/#44）—— **本系列 v5.4 報告的建議已落實**，codegen 終於看得到全部欄位
2. **延遲 98.2s，全系列最快**（−32%）
3. **收入桶飽和降至五輪最低**（完全飽和 2/8；趨勢 7→3→5→3→2）—— 但**未清零**，案例 02/05 仍 100%
4. `overshoot` 首次有**可判定的定義**（> 2×TARGET_MIN）
5. `no_op` 遙測持續準確；`dims_counted` 大致誠實（1 處不一致）
6. `score_scale: "不可跨版本比較"` 寫入契約 —— **而本輪分數果然又漂移，印證其必要**
7. 本輪**零錯誤**（9/9 200）

### v5.6 的問題 ⚠️
1. **`employment_status` 連續五輪從未被套用（0/8）** —— 橫貫全系列的未解問題
2. **重現性探針出現 75.00s 硬切、完全無 HTTP 回應**（transient）；對照 v5.4 的結構化 503，**疑似錯誤處理退步**（未證實同因）
3. **可重現性仍 4.4×**，且**版本內 top-3 交集仍多為 0–1/3** —— ranking 層不穩定五版皆未解
4. **`opMode` 預設值變更** —— 對未明傳該參數的 consumer 是 breaking change
5. **分數尺度持續漂移**（案例 04：4.86 → 2.54）—— 不可跨版本比較，下游絕對門檻會失效
6. **空轉率回升到 28%**（v5.3.1 為 10%）

### 五版演進一句話總結

> **v5.6 是「契約品質」與「效能」雙線最好的一版**：把 v5.4 遺留的「新欄位只寫在描述裡、codegen 看不到」正式型別化，並把延遲砍掉三分之一、收入桶飽和清零。
> **但橫貫五版的兩個結構性問題仍未動**：`employment_status` 從未被使用、以及 ranking 層的不可重現。
> 另新增兩個要注意的變化：`opMode` 預設值變更（breaking）與一次無 HTTP 回應的 75s 硬切事件。
