## 2. 【核心發現】v5.4 的契約變更 —— 直接回應了本系列前三輪的發現

`openapi.json` 由 9706 B → **10131 B**，sha256 改變 → **第三種契約**（v4.9.2 / v5.2=v5.3.1 / v5.4）。endpoint 與 query 參數**未變**；變更全在**回應 schema**：

### 2.1 新增欄位一覽

| 位置 | 新增 | 型別 | 描述（原文） |
|------|------|------|--------------|
| **top-level** | `pool_exhausted` | boolean, default `false` | 「符合條件人數 < top_k（系統拒絕為湊數放寬核心維度，故回傳較少；**#43**）」 |
| **top-level** | `returned` | integer, default `0` | 「實際回傳筆數（= len(summary)）；可小於 top_k，見 pool_exhausted（**#43**）」 |
| `broadening_attempts[]` | `no_op` | — | 該輪放寬是否無效果 |
| `broadening_attempts[]` | `overshoot` | — | 該輪放寬是否過頭 |
| `broadening_attempts[]` | `filters_changed` | — | 該輪是否真的改了 filter |
| `scoring_basis` | `weight_version` | string | 例：`"v5.4"` |
| `scoring_basis` | **`score_scale`** | string | **`"relative-within-version"`** |
| `scoring_basis` | `score_schema` | integer | 例：`1` |

### 2.2 這些欄位精準對應我前三輪報告的發現

| 我先前報告的發現 | v5.4 的對應 |
|------------------|-------------|
| v5.3.1 報告 §5.5：「案例 06 回傳 5 < top_k=10，**consumer 不可假設固定回傳數**」 | **`returned`** + **`pool_exhausted`**（且描述明引「#43」） |
| v5.2 報告 §5.4 / v5.3.1 報告 §5.3：「**空轉（inert）broadening 迴圈**」 | **`no_op`**（+ `filters_changed`） |
| v5.3.1 報告 §5.9：「**分數不可跨版本比較**，若下游有絕對門檻，升級會失效」 | **`score_scale: "relative-within-version"`** + **`weight_version`** + `score_schema` |
| （新增，主動） | `overshoot` |

→ **v5.4 把「人為判讀才知道的病理」變成機器可讀的遙測。** 這是本系列四輪中最明確的「回饋閉環」證據。

### 2.3 契約衛生的小瑕疵：新欄位只有文字描述，沒有機器可讀 schema

`broadening_attempts` 的 items 與 `scoring_basis` 在 OpenAPI 中仍被型別化為
`{"additionalProperties": true, "type": "object"}` —— **新欄位只出現在 description 字串裡，未列為 `properties`**。
→ 影響：**codegen / schema 驗證工具不會產生 `no_op`、`overshoot`、`score_scale` 等欄位**；consumer 必須靠讀描述或實際回應才能發現。建議改為顯式 `properties`。

## 3. 【首度出現】HTTP 503 `FILTER_FAILED`（案例 2 TESLA）

四輪共 36 次請求中**唯一的非 200**。原始回應（已完整保存於 `raw/02_tesla.body`）：

```json
HTTP/1.1 503 Service Unavailable   (uvicorn, application/json, 206 bytes, 260.59s)
{"detail":{"code":"FILTER_FAILED",
           "message":"無法從問題中解析出篩選條件（LLM 分析失敗且關鍵字解析無結果）",
           "details":"請確認 LLM API key / model 設定，或換一種問法"}}
```

**觀察**：
1. **耗時 260.6s 才失敗** —— 顯示是 LLM 側逾時/重試耗盡，而非立即拒絕。
2. **「TESLA的目標客戶」在 v4.9.2 / v5.2 / v5.3.1 三輪都成功**（top score 7.72 / 6.74 / 5.59）。**同一查詢在 v5.4 失敗** → 這是一次**可用性退步事件**（惟需注意 LLM 背景可能瞬時異常，非必為版本缺陷；但錯誤訊息指向 LLM 分析失敗）。
3. **關鍵字 fallback 無效**：訊息明載「關鍵字解析無結果」。查詢含 `TESLA`（拉丁字母）+ 中文，**fallback 解析器顯然處理不了這種混合字串** —— 這是可修復的具體缺陷。
4. **良好的工程面**：這是**結構化、有錯誤碼、有可行建議**的優雅失敗，不是 crash 或 500。503 也在 OpenAPI 中有宣告。

### ★ 契約違規：503 回應不符合自己宣告的 schema

| | 宣告（OpenAPI） | 實際回應 |
|---|---|---|
| 503 的 schema | `$ref: #/components/schemas/ErrorResponse` | — |
| `ErrorResponse` required | **`error`**（另有 `status` default `"error"`） | — |
| 實際 top-level keys | — | **`detail`** |
| 有 `error` 欄位？ | 應有 | **沒有（false）** |
| 有 `detail` 欄位？ | 未宣告 | **有（true）** |

→ **實際 503 body 用的是 FastAPI `HTTPException` 的 `detail` 包裝，與宣告的 `ErrorResponse`（要求 `error`）不符。** 這是可驗證的契約/實作不一致，**只有真的觸發錯誤才會發現**。
→ 影響：依 `ErrorResponse` 寫的錯誤處理程式碼會**取不到 `error` 而失敗**。

## 5. 核心發現

### 5.1 【驗證成功】`pool_exhausted` 語意經實測確認

新欄位的語意不能只靠描述相信，我用**定向探針**驗證：對窄查詢（醫美）請求 `top_k=100`，使 matched < top_k 必然成立。

```json
total_matched  = 12
returned       = 12
len(summary)   = 12
len(persona_ids)= 12
pool_exhausted = true      ← ★ 正確翻為 true
top_k requested= 100       (12 < 100)
```

→ **語意確認**：`pool_exhausted=true` ⇔ `matched < top_k`；且 `returned == len(summary) == len(persona_ids)` 不變式成立。
→ 主套件 7 個成功案例全為 `false`（皆 matched ≥ top_k）—— 因此**若沒有這個定向探針，就無法確認 true 分支真的會觸發**。此探針證據保存於 `probe/pool_exhausted_topk100.json`。

### 5.2 【改善】`debt_status` 回到硬篩選，精度恢復

v5.3.1 曾把 `debt_status` 從硬篩選改為純計分，導致案例 07「債務整合」的名單裡有 **4/10 完全無債務**（我上輪標為精度退步）。**v5.4 改回硬篩選**：

| | v5.3.1 | **v5.4** |
|---|---|---|
| 案例 07 `applied_filters.debt_status` | 無（已 relaxed） | **`["有房貸","房貸+消費債"]`** |
| 回傳 `debt_status` 分佈 | 有房貸 5、房貸+消費債 1、**無 4** | **有房貸 9、房貸+消費債 1、無 0** ✅ |
| 案例 05 | 無 | **`["有房貸","房貸+消費債"]`**（5 筆皆符合） |

→ **同時保留在 `dims_counted`**（案例 05/07 皆有）→ 篩選與計分並用，是比 v5.3.1 更完整的設計。

### 5.3 【改善】案例 06 醫美：由 v5.3.1 的退化 5 筆恢復到 10 筆，且核心維度未被放寬

v5.3.1 在此案例 matched 只有 5（< top_k=10），系統「拒絕放寬核心維度」而回傳 5 筆。
**v5.4 找到出路**：保留 `aesthetic_procedure=有`，改為放寬**非核心**維度。

```
loop 1:  3→10  移除 family_income（與 income 高度重疊，非核心）
loop 2: 10→13  刪除 clothing_spend（僅輔助篩選消費力）
loop 3: 13→13  no_op=true  放寬 age 新增 19-24 與 55-64（無效，已正確標記）
```

| | v5.3.1 | **v5.4** |
|---|---|---|
| matched / returned | **5 / 5** | **13 / 10** ✅ |
| `aesthetic_procedure` 篩選 | `有` | `有`（保留） |
| 回傳 aes 分佈 | 5/5 `有` | **10/10 `有`** ✅ |
| `pool_exhausted` | （欄位不存在） | `false` |

→ **v5.4 用「放寬非核心維度」取代「放棄」，同時保住核心維度的正確性** —— 兼顧精度與召回。

### 5.4 【驗證成功】`no_op` 標記準確

v5.4 有 12 個 broadening 迴圈，其中 **3 個** `match_count_before == match_count_after`（我人工判定的「空轉」），而宣告的 `no_op=true` **正好 3 個** → **人工判定與機器標記 100% 一致** ✅
（v5.3.1 亦同：實測 1 個空轉、宣告 1 個。）

**⚠️ 同時是對我上一輪報告的更正**：v5.3.1 **已經**會輸出 `no_op` 與 `filters_changed`（只是未寫進它的 OpenAPI 描述）。我在 v5.3.1 報告 §5.3 中用「`before==after` 人工計算空轉率」呈現，**未察覺該欄位已存在**。該結論（1/10、且該迴圈是刻意拒絕）**仍然正確**，但當時應直接引用 `no_op`。**`overshoot` 才是 v5.4 新增的。**

### 5.5 【新增能力】`overshoot` 標記

v5.4 案例 03 第 1 輪：`18→41`，**`overshoot=true`**（放寬幅度超出預期）。
其餘 11 個迴圈皆 `overshoot=false`。
→ 這是 v5.4 全新的遙測維度，用於偵測「放寬過頭」—— 本系列前三輪都無法觀測此現象。**在本次 12 個迴圈中出現 1 次。**

## 7. 結論

### v5.4 的實質改善 ✅

1. **★ 契約新增可觀測性欄位，且精準對應本系列前三輪的發現**（§2）：
   - `returned` + `pool_exhausted` ← 我上輪指出的「回傳數 < top_k 是契約風險」
   - `no_op` + `filters_changed`（v5.3.1 已有、v5.4 正式寫入描述）+ **`overshoot`**（新）
   - **`score_scale: "relative-within-version"`** + `weight_version` + `score_schema` ← 我上輪指出的「分數不可跨版本比較」
2. **`pool_exhausted` 語意經定向探針實測確認**（`12 < 100` → `true`），且 `returned == len(summary) == len(persona_ids)` 不變式成立 ✅
3. **`no_op` 標記與人工判定的空轉 100% 一致**（3 vs 3；v5.3.1 亦 1 vs 1）✅
4. **`debt_status` 回到硬篩選 → 精度恢復**：案例 07 由 v5.3.1 的「4/10 無債務」回到 **0/10 無債務** ✅
5. **案例 06 由退化 5 筆恢復到 10 筆**，且是**放寬非核心維度**而非放棄核心維度 —— 兼顧精度與召回 ✅
6. **`dims_counted` 維持修正**（0 不一致，同 v5.3.1）
7. **`aesthetic_procedure` 隨機套用的病理維持修復**（0/3）

### v5.4 的問題 ⚠️

1. **【新】HTTP 503 `FILTER_FAILED`** —— 四輪 36 次請求中唯一失敗；「TESLA的目標客戶」在前三輪皆成功。耗時 260.6s 才失敗，且**關鍵字 fallback 對 `TESLA`+中文混合字串失效**（確定缺陷）。
2. **【新】503 回應違反自身宣告的 schema** —— 宣告 `ErrorResponse`（required `error`），實際回傳 `detail`。**依契約寫的錯誤處理會取不到 `error`。**
3. **【退步】可重現性不如 v5.3.1** —— `total_matched` 變異 4.5×（v5.3.1 為 1.3×），且出現 1 次 300s 逾時。
4. **`employment_status` 四輪皆未被套用（0/8）** —— 橫貫四版的未解問題。
5. **空轉率 25%**（v5.3.1 為 10%）—— 回升。
6. **top-k persona 選擇仍高度不穩定**（三組配對重疊 0/3、0/3、1/3）—— 四版皆未解決，單次斷言式 QA 仍不可靠。
7. **新欄位僅有文字描述、無機器可讀 schema** —— codegen 不會產生 `pool_exhausted`/`score_scale` 等欄位。
8. **延遲 195.7s**（第二慢），接近 v5.2 水準。

### 四版演進一句話總結

> **v5.4 是四輪中「契約品質」最好的一版** —— 它把前三輪暴露的三個病理（回傳數不足、空轉放寬、分數跨版本誤用）**正式寫進 API 契約成為可觀測遙測**，並讓 `debt_status` 的精度與案例 06 的召回同時到位。
> **代價與代價外的問題**：可重現性較 v5.3.1 退步、空轉率回升、出現首個 503 且該錯誤回應違反自己的 schema、以及橫貫四版從未解決的 `employment_status`。
