# Persona DB — 驗證（QA）

> 觸發時機：跑出貨驗證、判讀驗證報告、寫新斷言、調查「好像壞了」的現象。
> 前置：`DATA-CONTRACT.md`（契約）＋ `persona-db-regen`（資料面）。

## 0. 驗證套件

```bash
bash upDockerVerHermes/test-persona-db-api.sh      # 9 案例 + 60+ 斷言（含主機層）
```
輸出會標示每條斷言的**掃描涵蓋數**（`掃描 9/9`）與**空轉**項目。**紅旗**要看五個：
`❌`（真失敗）／`⚠️`（需判斷）／`FILTER_FAILED`／`Traceback`／`no_op_limit`。

## 1. 斷言設計六規則

1. **掃描範圍 ＝ 全部案例**，並在輸出印 `掃描 N/M`。只掃子集 → 「未觸發 X」可能與事實相反、✅ 可能是空轉。
2. **「沒事件」要明示空轉**：`（空轉：本輪無事件 → 不具檢定效力）`，不可印 ✅ 假裝驗過。
3. **計數器正名到「路徑」層級**：同一個 `stop_reason` 可能有兩條路徑（例：`protected_veto` 有「硬 veto」與「模型主動拒絕」）
   → 分開列，並註明「兩者同時為真不矛盾」。
4. **口徑一致**：斷言用的基準要和產品用的相同（例：保護集上限以「請求開始」的維度數為基準
   → 斷言不可用回應的最終 `applied_filters` 重算）。歷史實例：過衝倍率在修正動作**之後**量測 → 誤報 1.0×。
5. **工具要雙向驗證**：掃描／檢查工具必須「乾淨的 0 命中、已知問題的必命中」才算驗過。
6. **斷言失敗先懷疑斷言**：跑一次 `python3 -c` 實測該斷言的前提，再判產品。

## 2. 三方分診（看到異常時的第一步）

| 症狀 | 先查 | 典型原因 |
|:--|:--|:--|
| **案例檔空 / `Expecting value: line 1 column 1`** | 服務是否起來（容器狀態、啟動 log） | **環境問題**（服務未就緒／連線失敗），不是 API 壞了 |
| **同一題每次結果不同** | 連跑 3 次看**機制性欄位**（`subject`／`protected_dims`／護欄是否成立） | **LLM 非確定性**（正常）；只有機制性訊號才算 regression |
| **斷言 ✅ 但數值怪 / 斷言 ❌ 但行為看起來對** | 斷言的掃描範圍與口徑 | **斷言問題**（涵蓋不足／基準不一致） |
| **護欄沒生效 / 保護維度被放寬** | 回應的 `protected_dims_sources`、伺服器端 log | **產品缺陷** → 開票（含修法＋驗證方式） |

## 3. 證據怎麼讀（這節最容易出錯）

- **log**：優先讀**原始 log 檔**（`docker inspect -f {{.LogPath}}`）；`docker logs` 可能因 log 檔中的 NUL hole
  **只吐出極少行**（實測 90/3103）→ 用它取樣會偽陰性。輸出要**標明來源**。
- **部署保真度**：比對 **tarball 內 `api/*.py` sha256 == 容器內 `/app/api/*.py`**（byte 級）——
  「版本字串對了」不等於「跑的是那顆包」。
- **版本一致性**：`容器 VERSION == RELEASE-VERSION == tag == tarball 內 VERSION == /openapi.json info.version`。
- **API 文件即契約**：`/openapi.json` 的 `info.version`／端點 `description` 都是可驗項目（例：`/docs` 是否內建操作重點）。

## 4. 判讀報告（含外部驗證者交來的報告）

1. 先看**紅旗統計**與**掃描涵蓋數**，再看結論。
2. **空轉項目**要點名，並說明「如何才算真的驗過」（多半是確定性單元測試，而非再跑 LLM 探針）。
3. **外部報告的每個 finding 先獨立複驗**（讀 code／實跑／取 log）再開票；報告的「無法驗證」也要複驗
   （很可能是**它自己的存取／量測條件**問題，換個路徑就能驗 → 這是常見的 false positive）。
4. **限制章節要寫「試過什麼」**（環境／帳號／認證）——否則讀者無法判斷這個 N/A 能不能被補上。
5. N=1 的數字類發現一律降級為**觀察**（LLM 抽樣變異）；機制性結論才可作為缺陷依據。

## 5. 撰寫驗證報告的最小結構

```
0. 目標與環境（版本、節點、執行位置、連線方式；受測產物 sha256）
1. 儀器（上游腳本 sha256、對上游的改動清單、忠實度證明）
2. 執行摘要（表格：matched/returned/loops/stop_reason/耗時）
3. 斷言結果（✅/❌/⚠️/N/A 統計 + 每條的掃描涵蓋數）
4. 回應分析（語意正確性、自證性、守恆不變式）
5. 驗證限制 / 未涵蓋（含「試過什麼」與空轉清單）
6. 結論（正面證據 / 需注意 / 空轉）
```

## 6. 開票紀律

- 每個缺陷**一個票**：症狀（附原始證據）＋ 根因 ＋ 建議修法 ＋ **驗收標準** ＋ 影響範圍。
- 架構性／取捨限制用 `known-limitation`，不當 bug。
- 驗證通過才關票；關票要附**三層證據**（單元／真 LLM e2e／部署 SOP）。
- 「已知限制」與「修正紀錄」寫進 `RELEASE-*.md`／`persona-db.md`，讓後人不必重踩。
